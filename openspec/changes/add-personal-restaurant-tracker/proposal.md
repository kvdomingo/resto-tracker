## Why

Deciding where to eat means digging through screenshots, bookmarks, and
half-remembered recommendations. There is no single place to record "we tried
this and it was great" next to "we still want to try this", with the details
that actually matter at decision time: where it is, what kind of food it serves,
how expensive it is, and a link to the menu.

This change builds the first working slice of that app: a shared restaurant
catalogue anyone can browse on a map, sign-in so people can add restaurants and
review them, and a personal tried / want-to-try list over that catalogue. Shared
group collections are the eventual goal, but they are worthless without a
catalogue and a personal list underneath them, so those come first.

## What Changes

- Repository structure: `api/` (FastAPI), `ui/` (TanStack Start in SPA mode),
  `infra/helm/resto-tracker/` (Helm), a root `docker-compose.yml` for local
  development, a root `Taskfile.yml`, and `mise.toml` for tool versions.
- PostgreSQL 18 schema with PostGIS, managed as dbmate SQL migrations. All query
  code is generated by `sqlc-gen-python` and runs over SQLAlchemy's async engine
  as a connection layer only. There are no ORM models.
- Authentication delegated to Stytch OAuth, brokered by the backend. The session
  lives in a signed HTTP-only cookie. A local `users` row keyed by the provider
  user ID gives authored content a stable author.
- Shared restaurant catalogue: name, price tier (1–5), one or more labelled
  branches with map coordinates, and tags are required. Website, menu URL,
  Instagram handle, and a reservations-required flag are optional. Anyone can
  browse. Signed-in users can add restaurants, and only a restaurant's creator
  can edit or delete it.
- Map browsing: the home page lists the restaurants whose branches fall inside
  the visible map area, with pins, search, and tag filters.
- Reviews: signed-in users rate restaurants 1–5 with text, optionally posting
  anonymously.
- Personal list: each user marks catalogue restaurants `tried` or `want_to_try`,
  privately, and can filter and search their list.
- Frontend: TanStack Start and Router, server state in TanStack Query through a
  client generated from the backend's OpenAPI schema, URL state in validated
  router search params, the add/edit form in TanStack Form, and maps with mapcn
  over MapLibre GL.
- Deployment path: a single Docker image in which the backend serves the built
  SPA, plus a Helm chart for a Kubernetes cluster with an external managed
  Postgres. The chart ships an HPA (2–5 replicas), a PodDisruptionBudget, and
  resource requests and limits.

Non-goals for this change: group behaviour and shared collections (the `groups`
tables exist but nothing uses them), photo uploads, moderation of catalogue
content, and any public profile or social feed.

## Capabilities

### New Capabilities

- `user-auth`: Stytch-backed sign-in, cookie sessions, the local user record,
  and the access rules (anonymous browse, signed-in write, creator-only
  edit/delete, private personal lists).
- `restaurant-catalog`: The shared restaurant domain (name, price tier,
  branches, tags, optional links), creator-managed create/edit/delete, map-area
  browsing, and reviews.
- `personal-list`: A user's private tried / want-to-try statuses over the
  catalogue, plus filtering and listing over them.

### Modified Capabilities

None. This is the first change in the repository.

## Impact

- **New dependencies**: Backend: `fastapi[standard]`, `asyncpg`, `sqlalchemy`,
  `geoalchemy2`, `shapely`, `stytch`, `pydantic-settings`, `itsdangerous`,
  `loguru`, and `scalar-fastapi`. Build-time codegen uses `sqlc` with a fork of
  `sqlc-gen-python` (`kvdomingo/sqlc-gen-python`). `dbmate` runs migrations.
  Frontend: `@tanstack/react-start`, `@tanstack/react-router`,
  `@tanstack/react-query`, `@tanstack/react-form`, `tailwindcss`,
  `shadcn/ui`, `maplibre-gl` (via mapcn), `zod`, and `openapi-fetch` with
  `openapi-react-query`. `openapi-typescript` is build-time codegen. Bun is the
  package manager and dev runtime.
- **External services**: A Stytch project with an OAuth provider configured
  (test for local dev, live for production) is required before anyone can sign
  in. Map tiles come from Carto basemaps.
- **Infrastructure**: PostgreSQL 18 with the `postgis`, `pg_idkit`, `citext`,
  and `pg_trgm` extensions. Local dev uses `ghcr.io/kvdomingo/postgresql-pig:18`.
  Production needs a managed instance that offers all four, and `pg_idkit` is
  not commonly available (see `design.md`).
- **Secrets**: `DATABASE_URL`, `SECRET_KEY`, the Stytch project ID, public token,
  and secret, the OAuth callback URL, and `APP_URL` come from the
  `resto-tracker` Infisical project in every environment. Locally the dev
  containers run under `infisical run`. In the cluster, an `InfisicalSecret`
  syncs them into a Kubernetes Secret. No secret material lives in Git or in
  chart values.
- **Tooling**: Task (`taskfile.dev`) runs local workflows, mise pins tool
  versions, and prek runs pre-commit hooks (ruff, ty, sqlfluff, biome).
- **Cluster conventions**: The chart in `infra/` is the source of truth and Argo
  CD syncs it. No `helm` command runs against the cluster. The deployment tracks
  the `latest` image tag and Keel rolls it out on a new digest, so most deploys
  are not git syncs at all. See `design.md` for what that forces on migrations,
  rollback, and drift.
- **Forward compatibility**: Personal-list status already lives in its own
  per-user table, and the `groups` tables are in place, so group collections can
  be added without rewriting the restaurant tables.
