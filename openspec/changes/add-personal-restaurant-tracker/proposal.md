## Why

Deciding where to eat means digging through screenshots, bookmarks, and
half-remembered recommendations. There is no single place to record "we tried
this and it was great" next to "we still want to try this", with the details
that actually matter at decision time: where it is, what kind of food it serves,
and a link to the menu.

This change builds the first working slice of that app: sign in, add
restaurants, and keep a personal tried / want-to-try list. Shared group
collections are the eventual goal, but they are worthless without a restaurant
catalogue and a personal list underneath them, so those come first.

## What Changes

- New repository structure: `backend/` (FastAPI), `frontend/` (Vite + React),
  `infra/` (Helm), and a root `docker-compose.yaml` for local development.
- New PostgreSQL schema managed as plain SQL migrations, with all query code
  generated by `sqlc-gen-python`. No ORM.
- Authentication delegated to Stytch. The backend keeps a local `users` row
  keyed by Stytch user ID so that restaurants and list entries have a stable
  owner; Stytch owns credentials, sessions, and account recovery.
- New restaurant domain: name, one or more named locations with coordinates, and
  tags are required; image, website, Instagram, and menu links are optional.
  Restaurants are owned by the user who created them.
- New personal list: each restaurant a user has added carries a status of
  `tried` or `want_to_try`, filterable and sortable in the UI.
- New frontend: authenticated shell, restaurant list and detail views, an
  add/edit form built with TanStack Form, server state via TanStack Query over a
  client generated from the backend's OpenAPI schema, and a map picker for
  locations using mapcn.
- New deployment path: single Docker image for backend and frontend (frontend is
  served by the backend), plus a Helm chart targeting a Kubernetes cluster with
  an external managed Postgres. The chart ships an HPA (2–5 replicas), a
  PodDisruptionBudget, and resource requests and limits.

Non-goals for this change: groups and shared collections, ratings and reviews,
photo uploads to object storage, restaurant search across other users' entries,
and any public/social surface. The data model leaves room for groups (see
design), but no group behaviour ships here.

## Capabilities

### New Capabilities

- `user-auth`: Stytch-backed sign-in and session verification, and the local
  user record that every owned resource points at.
- `restaurant-catalog`: The restaurant domain — required name, locations, and
  tags; optional image and links — including creating, editing, and deleting
  restaurants a user owns.
- `personal-list`: A user's collection of restaurants with tried / want-to-try
  status, plus filtering and listing over it.

### Modified Capabilities

None — this is the first change in the repository.

## Impact

- **New dependencies**: Backend — `fastapi`, `uvicorn`, `asyncpg`, `stytch`,
  `pydantic-settings`; `sqlc` and `sqlc-gen-python` as build-time codegen;
  `dbmate` as the migration runner. Frontend — `@stytch/react`,
  `@tanstack/react-query`, `@tanstack/react-form`, `tailwindcss`, `shadcn/ui`,
  `mapcn`, `openapi-fetch` and `openapi-react-query` at runtime with
  `openapi-typescript` as build-time codegen.
- **External services**: A Stytch project (test environment for local dev, live
  for production) is required before anyone can log in. Map tiles from
  OpenFreeMap.
- **Infrastructure**: PostgreSQL 18. Local dev runs it in Docker Compose;
  production expects a managed instance reachable by the cluster.
- **Secrets**: Stytch project ID and secret, and the database URL, come from
  `.env` locally and from Infisical in the cluster — an `InfisicalSecret`
  resource syncs a `resto-tracker` project into a Kubernetes Secret the pods
  consume. No secret material in Git or in chart values.
- **Tooling**: Task (`taskfile.dev`) is the task runner for codegen, builds, and
  local workflows.
- **Cluster conventions**: `infra/` is the source of truth and Argo CD syncs it
  — no `helm` command runs against the cluster. The deployment tracks the
  `latest` image tag and is rolled by Keel on a new digest, so most deploys are
  not git syncs at all — see `design.md` for what that forces on migrations,
  rollback, and drift.
- **Forward compatibility**: Ownership is modelled so that group ownership can
  be added later without rewriting the restaurant tables — see `design.md`.
